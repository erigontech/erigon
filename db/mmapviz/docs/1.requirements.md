# mmapviz requirements

This document is the authority on *what mmapviz must do and why*; `2.visualisations.md`,
`3.design.md`, and `4.testing.md` are the responses to it (traceability in §6). Background on the
OS mechanics: `0.background.md`.

## 1. Why we are doing this

Erigon's entire storage layer is mmap-backed: every snapshot file (state domains/history/inverted
indices, block segments, caplin, heimdall) and every MDBX database (chaindata, txpool, devp2p
`nodes/*`, caplin stores, polygon-bridge, heimdall, downloader, …). mmap delegates caching and IO
to the OS — which is the design's strength, but it makes behaviour invisible: reads don't appear
in our code as IO calls, cache contents are decided by kernel reclaim, and standard process
metrics (RSS, `process_io`) can't say *which file*, *which region*, or *why*.

We want a visualisation mechanism for our IO and page-cache interactions good enough to act on:

- **identify file formats that behave poorly** under real access patterns (e.g. an index whose
  layout scatters hot entries across the whole file, defeating the cache), and
- **identify code that is inefficient in IO/page-cache terms** (e.g. a path that re-reads
  regions the cache keeps evicting, or touches far more data than it needs),

so that follow-up work (format changes, access-pattern fixes, madvise/pinning policy) can be
targeted by evidence instead of guesswork.

## 2. Core questions mmapviz must answer

1. Which files sit in the OS page cache, and how much of each, **at any point in time** — now,
   and at any past moment within retention.
2. Which **segments/regions of those files** are cached (and were cached, over time).
3. Who are the **top IO users** — which files take the most physical IO, and which process/role
   causes it — so attention goes to the right place fast.
4. **Why** did that IO happen instead of the page cache absorbing it — warmup (first touch),
   thrash (data evicted and re-read), writeback, or code simply requesting too much.
5. What did all of the above look like **when block N executed** — and was an IO burst caused by
   execution — including **unwind + re-exec episodes** after a reorg — or by the node's
   **background jobs**: file merges (e.g. `accounts.0-1` +
   `accounts.1-2` → `accounts.0-2`), collations (extracting a new step of data from MDBX into
   the next step file), prunes (deleting a collated step from MDBX afterwards, in background
   post-FCU processing), **torrent seeding** — the bittorrent downloader serving snapshot
   data to other peers reads our files through the same page cache, driven by peer demand rather
   than anything our node is doing — and **devp2p serving**: answering peers' eth-protocol
   requests (headers/bodies/transactions/receipts) reads block and receipt classes through the
   node's own mmap'd readers, likewise on peer demand. Cache/IO state must be correlatable with
   node activity, not just wall-clock time.

## 3. Functional requirements

- **FR1 — Coverage.** Automatically discover and observe *all* snapshot files and *all* MDBX
  databases under each configured datadir, including envs outside any catalog (devp2p
  `nodes/<protocol>`, caplin per-store envs). New files/envs appear without configuration; no
  silent omissions. Configured datadirs need not be erigon's: pointing `--datadir` at a
  coresident client's directory (e.g. lighthouse/prysm when running externalcl) tracks its files
  too — the junk-tolerant classifier degrades them to ext-only labels with full
  residency/thrash/IO fidelity.
- **FR2 — Residency.** Per-file page-cache residency, dirty, and writeback bytes at sampling
  cadence, aggregated to file classes for fleet metrics.
- **FR3 — Regions.** Per-file offset-resolution residency (which parts of the file are cached),
  recorded over time.
- **FR4 — IO attribution.** Per-file physical fill/evict volumes (bytes, including readahead),
  and per-consumer (process role) fill attribution.
- **FR5 — History.** FR2–FR4 persisted locally with bounded retention; queryable at any past
  instant (scrubber), over ranges (trends, top movers), and as two-point diffs.
- **FR6 — Node-activity correlation.** Record activity streams alongside samples: (a) chain
  position (head / execution block), (b) **file-merge events** (input files → output file,
  time span), (c) **collation events** (entity, step — MDBX → next step file), (d) **prune
  events** (entity, step range deleted from MDBX; runs in background post-FCU processing);
  and (e) **unwind + re-exec episodes**, derived from the chain-position stream. Unwind and
  forward exec run as one pipeline (the node either just execs forward, or — given another
  fork — unwinds backward then execs forward), so an episode spans the backstep plus the
  forward catch-up, closing when progress returns to tip cadence; depth = prior position −
  unwind target. Also (f) **host & neighbor pressure context**: per-sweep host reclaim/pressure
  counters (`MemAvailable`, PSI, `pgscan_*`, `workingset_refault_file`) always, and — opt-in —
  sibling cgroups' `memory.current`/`memory.pressure`, so "who is growing vs who is suffering"
  (e.g. an external CL such as lighthouse/prysm on the same host) is scrubbable in the same
  store and joinable against exec/merge/collation/prune/unwind spans. And (g) **torrent
  activity**: the downloader's upload (seeding) and download rates recorded as a stream, so
  fills on cold snapshot classes can be attributed to peer demand rather than node work; plus
  (h) **devp2p egress**: outbound p2p bytes/s (per-message counters where exposed) as the
  correlation stream for peer-serving IO on block/receipt classes. Every time-based view can label time T with block
  N and overlay job/episode spans; "state when block N executed", "IO during merge/collation/
  prune X", and "IO during unwind episode E" are supported lookups. Unwinds also make block↔time
  non-monotonic; lookups must return the matching interval(s), not assume monotonicity. The
  mechanism should extend to other step-lifecycle jobs (index build) without redesign.
- **FR7 — Explainability.** Classify per-class/per-file fills into warmup (first touch),
  refault/thrash (recently evicted, re-read — the avoidable kind), steady-state, and
  background-job (inside FR6 merge/collation/prune spans); deletion-invalidated evictions
  classify as deleted, never as thrash (FR11). When the node's logical read metrics
  (`kvmetrics`, `KV_READ_METRICS`) are enabled, logical reads must be joinable against physical
  fills to separate "code asked too much" from "cache couldn't hold it".
- **FR8 — Top-users views.** Ranked views (by fill bytes, eviction churn, residency delta) over
  a selectable time window, at class, file, and consumer granularity.
- **FR9 — Fleet correlation.** Class-level rollups exported as Prometheus metrics so cache/IO
  behaviour sits next to every existing node metric in Grafana, with alert rules attachable.
- **FR10 — Ad-hoc mode.** A one-shot CLI (table / JSON / offset heatmap) usable on any datadir
  with nothing deployed.
- **FR11 — Merge awareness.** Snapshot merges continuously replace smaller files with bigger
  ones — the range partitioning itself changes, files disappear and new ones appear. History of
  disappeared files stays queryable within retention; past layouts render as they were; class
  views stay continuous across re-partitioning (a stable step/block axis, not per-file rows);
  and merge-induced IO — deletion evictions, new-file warmup — is classified distinctly, never
  misread as cache pressure (feeds FR7).

## 4. Non-functional requirements

- **NFR1 — Minimal interference (hard requirement).** Zero code and zero behaviour change in the
  node; no locks shared with it (no datadir lock, no snapshot/DB opens); measurement must not
  fault pages in (no observer effect); sampling CPU self-limited (≤ 0.5 % of one core target)
  and externally cappable; the node must run identically with or without the sidecar.
- **NFR2 — Privileges.** Everything except IO tracing runs unprivileged as the datadir owner;
  IO tracing may require `CAP_BPF`+`CAP_PERFMON` and degrades gracefully when absent.
- **NFR3 — Deployment.** One sidecar process per host (the `erigon` binary, one command) covers
  all local datadirs/nodes; runs beside live nodes; also works against a stopped node's datadir.
- **NFR4 — Footprint.** History store bounded (size cap + retention, tens of MB/day typical);
  flat sidecar RSS/fd usage over weeks.
- **NFR5 — Robustness.** Tolerates node restarts, snapshot merge churn, and its own crashes;
  store corruption recovers by wipe-and-restart (observability data, not consensus data);
  disk-full degrades to metrics-only, never crash-loops.
- **NFR6 — Platform.** Full function on Linux ≥ 6.5 (fleet: 6.8); degraded (or disabled, loudly)
  on older kernels; non-Linux builds stub out cleanly.
- **NFR7 — Fidelity.** History granularity = sampling cadence (default 1–5 min, configurable);
  IO counters near-real-time (~15 s drains); activity annotations polled on their own faster
  cadence (~15–30 s, one cheap HTTP GET) so block correlation is accurate to one poll and short
  unwind episodes register — episodes shorter than the poll interval may still be missed.

## 5. Non-goals (v1)

- Acting on findings (madvise/mlock/pinning policy, format changes) — mmapviz informs that work,
  it doesn't do it.
- New instrumentation inside node read/write paths (`kvmetrics` already exists for the logical
  side).
- Cross-host aggregation UI — in v1 (per-host UI; the fleet view is Grafana over FR9 rollups).
  A centrally hosted UI on our domain that many sidecars plug into is an **anticipated
  evolution**: v1 must not preclude it, which is why the UI is a static bundle over a versioned,
  additive-only API with a meta/capabilities endpoint (`2.visualisations.md` §5).
- OpenTelemetry — v1 exports Prometheus metrics + JSON APIs only (an OTel collector can already
  ingest the Prometheus endpoint with no code from us). OTLP export of the *aggregate* layer
  (class rollups, activity spans) is a candidate egress for a future fleet/hosted iteration —
  an optional adapter at the edge, never the internal data model: strips/regions/joins don't
  fit OTEL's signals. OTEL *tracing* as a code-path→IO attribution mechanism was evaluated and
  not adopted — the missing link is kernel↔goroutine context, not span format
  (`3.design.md` §7); the kvmetrics-style source-tag route (Phase 4) reaches the same
  attribution robustly.
- Long-term archival (retention is days–weeks; JSON export is the escape hatch).
- General-purpose dashboards/query language, auth, multi-user features.
- Windows/macOS support.

## 7. Success criteria

- **S1** — On a live archive node, all five §2 questions are answerable from the UI/dashboard
  with zero node changes, and the NFR1 interference budget is verified (soak with latency
  non-regression).
- **S2** — Given a block number N, the UI retrieves the cache/IO layout at its execution time
  within one annotation-poll interval (NFR7).
- **S3** — Pilot produces at least one actionable, evidence-backed finding of the intended kind
  (e.g. "class X refaults Y GiB/h during execution — working set exceeds its cache share", or
  "path Z re-reads region R every block", or "each collation of entity E scans Y GiB of
  mdbx.dat"), demonstrating the tool meets its purpose (§1).
- **S4** — Top-IO-users ranking cross-checks against device-level truth (`iostat`,
  `process_io`) within tolerance.
