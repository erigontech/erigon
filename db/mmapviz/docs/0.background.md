# mmapviz background: Linux memory accounting, mmap, and the page cache

Companion to `3.design.md`. That doc decides *what to build*; this one explains the OS mechanisms
its metrics are built on, and what the various "how much memory" numbers actually mean. Nothing
here is erigon-specific except the **Relevance** callouts, which tie each mechanism to the
mmapviz metrics.

## 1. Virtual memory basics

A process sees a private virtual address space. The kernel tracks it as a list of **VMAs**
(virtual memory areas) — you can read them in `/proc/<pid>/maps`: each line is an address range,
permissions, and what backs it (a file + offset, or nothing = "anonymous").

**Virtual→physical translation** happens in units of **pages** (4 KiB on our fleet), through
**page tables**: a per-process radix tree, four levels deep on x86-64 (PGD → PUD → PMD → PTE),
where the leaf — the **page-table entry (PTE)** — holds the physical frame number plus permission
and accessed/dirty bits. The MMU walks this tree in hardware on every access and caches
translations in the **TLB**, so the walk is rarely paid twice. If the walk finds no valid PTE,
the CPU traps into the kernel: a **page fault** — the hook on which all of demand paging (§3)
hangs.

A real excerpt from a running erigon's `/proc/<pid>/maps` (one line per VMA):

```
address range              perms offset   dev   inode      path
6e4efa600000-6e4fbc908000  r--s  00000000 09:03 130173913  .../snapshots/v1.1-000000-000100-transactions.seg
6e4fbca00000-6e507ed08000  r--s  00000000 09:03 130173913  .../snapshots/v1.1-000000-000100-transactions.seg
00404000-02b57000          r-xp  00004000 09:03 8197263    .../build/bin/erigon
```

Perms: `r`ead/`w`rite/e`x`ecute plus `s`hared or `p`rivate (§ mapping modes below). Note the
first two lines: the *same* snapshot file — same device `09:03`, same inode `130173913` — mapped
twice at different addresses. That is the Decompressor's main map plus its transient sequential
view, live; one physical copy in the page cache, two windows onto it (and RSS counts it twice —
§4).

`mmap(file)` only creates a VMA — address space, no RAM, no IO. The first access to each page
faults it in on demand ("demand paging"). `munmap` removes the VMA; whatever physical copies
exist in the page cache are unaffected.

Two kinds of memory:

- **Anonymous** — heaps, stacks, the Go runtime's arenas. Backed by RAM (and swap, if any).
- **File-backed** — every mmap'd file. Backed by the file itself; RAM is just cache.

**Files, names, and inodes.** On disk, a file *is* an **inode**: the filesystem object holding
the data blocks and metadata, identified by a number unique within its filesystem — so
`(device, inode#)` is a file's global identity. Paths are just directory entries pointing at
inodes: a hardlink is a second name for the same inode; a rename changes only the name; a delete
removes a name, and the inode (with its data) survives until the last name, open fd, and mapping
are gone. The page cache is keyed by **inode, not path** — which is why renames don't move
cache, why every mapping and `read()` of one file shares the same pages, and why mmapviz dedupes
and attributes everything by `(dev, ino)`.

`mmap` takes two orthogonal flag sets. **`PROT_*`** sets the page permissions the MMU enforces
via the PTEs: `PROT_READ` allows loads, `PROT_WRITE` allows stores, `PROT_EXEC` allows execution;
`PROT_READ|PROT_WRITE` is simply both bits OR-ed together — an ordinary read-write mapping.
**`MAP_SHARED`/`MAP_PRIVATE`** sets where stores land:

- **`MAP_SHARED`** — the mapping is a window onto *the* page cache page for that file offset.
  Everyone mapping or `read()`-ing that offset sees the same physical page; a store through the
  mapping dirties the shared page. Erigon's data files are `PROT_READ, MAP_SHARED`
  (`common/mmap`, edsrzf); MDBX with `writemap=ON` (our default) is `PROT_READ|WRITE, MAP_SHARED`.
- **`MAP_PRIVATE`** — copy-on-write: first store creates a private anonymous copy. Not used for
  erigon data.

**VSZ** (virtual size) is computed as the sum of the sizes of all VMAs — every byte of mapped
*address space*, counted whether or not it was ever touched, is resident, or even exists in the
file yet. Address-space reservation is free (it creates VMAs, not memory), and MDBX reserves its
whole geometry up front — so a node's VSZ can read tens of TB while touching a fraction of it.
VSZ is noise; ignore it.

**Relevance:** every mmapviz target is a `MAP_SHARED` file mapping, so "how much RAM does this
file use" is a property of the *page cache, keyed by inode* — not of any process. That is what
lets the sidecar measure from outside the node, and why `pagecache_*` metrics are
process-independent (`3.design.md` §2).

## 2. The page cache

The page cache is the kernel's cache of file contents, keyed by `(inode, page index)`. *All*
buffered file IO goes through it — `read()`/`write()`, mmap faults, readahead — and there is one
physical copy per file page no matter how many processes, mappings, or fds touch it. Modern
kernels manage it in **folios** (a folio = 1..N physically contiguous pages; tracepoints report
an `order`, i.e. folio size).

A cache page moves through a small state machine:

```
                 fill (fault / read() / readahead)
      absent ────────────────────────────────────► resident, clean
   (+shadow if                                        │      ▲
    evicted before)                        store/write│      │ writeback done
                                                      ▼      │
                                                    dirty ──► writeback
      absent ◄──────────────────────────────── resident, clean
                 reclaim evicts (leaves a shadow entry)
```

The pieces that matter to us:

- **Fill paths**: (a) a page fault from a mapping, (b) buffered `read()`, (c) **readahead**
  around either. Erigon deliberately suppresses readahead almost everywhere (`MADV_RANDOM`
  baseline on its maps, MDBX `NoReadahead`), so fills track what was actually touched.
  Not to be confused with **fault-around**: when a fault hits a file mapping, the kernel maps
  not just the faulting page but up to `fault_around_bytes` (64 KiB = 16 pages on our hosts) of
  its neighbors — *only those already sitting in the page cache* — into the page table in the
  same trap. It is PTE batching to save future minor faults: it never does IO, so it changes RSS
  granularity (RSS grows in ~64 KiB steps around touched offsets) but never fills.
- **Aging & reclaim**: the kernel ranks cache pages by recency using accessed bits. Classic
  kernels keep two LRU lists (inactive → promoted to active on reuse); our fleet's 6.8 kernels
  run **MGLRU** (fully enabled, `/sys/kernel/mm/lru_gen/enabled = 0x7`), which generalizes this
  to age *generations* — same idea, better scan efficiency. Reclaim has two actors: **kswapd**
  wakes in the background when a zone's free memory crosses its **watermarks** (min/low/high;
  spacing tuned by `vm.watermark_scale_factor`) and evicts coldest-first; if allocation outruns
  it, the allocating task performs **direct reclaim** itself — a synchronous stall, the moment
  "someone else's allocation" becomes *our* latency (`pgscan_kswapd` vs `pgscan_direct` in
  `/proc/vmstat` distinguish the two). What gets reclaimed: clean file pages are dropped
  instantly — they can always be re-read — dirty ones must be written back first, and anonymous
  pages need swap. **Our hosts run no swap**, so `vm.swappiness` is moot and reclaim ≈ file-cache
  reclaim only: under pressure, erigon's mapped files *are* the reclaim pool. This is why a
  file-heavy process "shrinks gracefully", and why eviction is invisible to the application
  except as refault latency.
- **Shadow entries**: when a file page is evicted, the kernel leaves a tiny marker in the cache
  index recording roughly *when* (in reclaim terms) it left. If the page is filled again soon,
  the kernel detects a **refault** — proof the working set doesn't fit in RAM. `cachestat(2)`
  exposes exactly this: `nr_evicted` (pages currently absent that have shadows) and
  `nr_recently_evicted` (absent pages whose return would count as an active-use refault).
- **Dirty & writeback**: a store through a shared mapping or a `write()` marks the page dirty.
  Background flushers write dirty pages back by age/ratio thresholds (`vm.dirty_*`), or the
  application forces it: **`fsync(fd)`** blocks until the file's dirty pages *and* metadata are
  durably on disk, **`fdatasync`** skips non-essential metadata, and **`msync(addr, len,
  MS_SYNC)`** is the same durability contract expressed through a mapped range instead of an fd.
  MDBX commits issue these per its durability mode — that is what a commit's IO burst is. Pages
  with flush IO in flight are in **writeback**; once clean they're cheap to evict again.
- **The cache outlives processes**: closing fds, unmapping, or exiting drops nothing. Pages of a
  *deleted* file are freed once the last fd/mapping is gone. (`echo 3 > /proc/sys/vm/drop_caches`
  force-drops clean cache system-wide — instant "free RAM", followed by a refault storm; useful
  for cold-start experiments, never for prod nodes.)

**Relevance:** `pagecache_resident/dirty/writeback_bytes` are these states per file class, read
via `cachestat`; `pagecache_evicted/recently_evicted_bytes` are the shadow-entry signals (thrash
detection with no privileges); the `--trace.io` counters are the two *transitions* — the
`mm_filemap_add_to_page_cache` / `mm_filemap_delete_from_page_cache` tracepoints fire exactly on
the fill and evict edges of the diagram.

## 3. Page faults: minor vs major

- **Minor fault**: the page is already in the page cache (or is a zero/COW page) — the kernel
  only fixes up the PTE. Sub-microsecond-ish; no disk.
- **Major fault**: the page is absent — allocate a folio, submit a disk read, block the faulting
  thread until it completes. This is where mmap read latency lives.

Cold mmap read, end to end: access → MMU miss → fault handler → cache miss → IO submitted →
`mm_filemap_add_to_page_cache` → PTE installed → instruction retried. Warm read: access → fault →
cache hit → PTE installed (minor). Note reclaim may *unmap* PTEs while leaving pages cached —
then the next touch is a cheap minor fault, not IO; that's also why a process's RSS can fall with
zero performance impact.

**Relevance:** `--trace.io` fill bytes ≈ major-fault volume per file class (plus any residual
readahead). The existing per-process majflt panel (getrusage) is the same phenomenon without file
attribution — the two should move together. High fills + high `recently_evicted` on one class =
its working set is being squeezed; high fills right after restart = normal warmup.

## 4. Process-side accounting: RSS, PSS, and smaps

**RSS** — "resident set size", what `top` shows as RES and `ps` as RSS — is the OS's answer to
"how much RAM is this process using right now": the total size of the pages that are both
**physically in RAM** and **currently mapped in this process's page tables**. Anonymous and file
pages count alike; what does *not* count is anything mapped but never touched (that's only VSZ),
evicted, or swapped out. For erigon, RSS is dominated by evictable shared file pages
— which is why "erigon eats all my RAM" reports are usually a misreading. RSS diverges from
cache truth in every direction:

- Pages can be cached but **not in RSS**: readahead the process never touched, pages another
  process faulted, pages whose PTEs reclaim removed.
- Pages can be counted in RSS **more than once**: RSS is per-PTE, so the same physical page
  mapped through two VMAs — e.g. a Decompressor's main map plus its transient sequential view of
  the same file — counts twice.
- RSS can drop with no eviction at all (PTE reclaim, above).

`/proc/<pid>/smaps` breaks RSS down per VMA and adds:

- **PSS** ("proportional set size"): each page's size divided by its total map count. Summing
  PSS across processes (plus unmapped cache) approximates physical truth. This matters whenever
  several processes map the same files — a separately-run rpcdaemon on the same datadir, or the
  sidecar's own transient heatmap mappings.
- **Shared/Private_Clean/Dirty**: "shared" here means *map count > 1*, not `MAP_SHARED` — a
  shared-mode page mapped by one process shows as Private. With MDBX `writemap=ON`, commit
  activity appears as `Shared_Dirty`/`Private_Dirty` on the mdbx.dat VMA.
- **Referenced**: bytes with the accessed bit set since the last reset via
  `/proc/<pid>/clear_refs` — the classic working-set-size estimation trick. Resetting interferes
  with the kernel's own aging; we don't use it.

**Relevance:** this is precisely why mmapviz is *not* built on smaps: smaps answers "what does
this process have mapped right now" (per VMA, page-table walk, `mmap_lock` held, seconds on
TB-scale maps), while the design needs "what does this *file* occupy in cache" (per inode,
`cachestat`, cheap). The node's existing `mem_rss`/`mem_pss` gauges (from `diagnostics/mem`,
which reads smaps process-wide) stay on the dashboard as the process-view context.

## 5. System and cgroup view

- `/proc/meminfo`: `Cached` (page cache, including tmpfs), `Dirty`, `Writeback`, and
  **`MemAvailable`** — the reclaimable+free estimate. Watch `MemAvailable`, never `MemFree`: a
  healthy file-heavy host runs near-zero free with most RAM in cache.
- **cgroups** ("control groups"): the kernel's mechanism for grouping processes and
  metering/limiting the *group's* resources (memory, CPU, IO). A tree exposed as a filesystem at
  `/sys/fs/cgroup` (v2, unified, on our fleet), driven by file ops: `mkdir` = new group, write a
  PID to `cgroup.procs` to move a process in, write `memory.max`/`cpu.max` to limit, read
  `memory.current`/`memory.stat`/`*.pressure` for accounting. systemd puts every service in its
  own cgroup (unit options like `MemoryMax=`/`CPUQuota=` are these files); a container is
  essentially a cgroup plus namespaces. What matters here: `memory.current` *includes* page
  cache, charged to the cgroup that first touched each page; `memory.stat` splits out `file`,
  `active_file`, `inactive_file`; and `memory.max` on a node's cgroup therefore limits its cache
  too — reclaim then happens *inside* the cgroup even when the host has free RAM (an
  accidentally capped node thrashes while `MemAvailable` looks healthy).
- **PSI** (`/proc/pressure/memory`, `/proc/pressure/io`, and per-cgroup): fraction of time tasks
  stalled on reclaim/IO. The cleanest "are we actually suffering" signal.

**Can we tell when the page cache is being squeezed by *other* processes?** Yes — by
triangulation, because the kernel does not record *why* an individual page was evicted:

- **Victim side (per file class — this is mmapviz's contribution):** `recently_evicted` rising
  on our classes while their fills/refaults rise too = *our* working set is being pushed out
  and re-read.
- **Host side (is there pressure at all):** `MemAvailable` falling; PSI memory climbing;
  `/proc/vmstat` reclaim counters — `pgscan_kswapd`/`pgsteal_kswapd` (background reclaim
  volume), `pgscan_direct` (allocations stalling on synchronous reclaim — latency, and nonzero
  on our fleet hosts today), `workingset_refault_file` (the kernel's own global refault count).
- **Culprit side (who caused it):** correlation — another process's anonymous RSS growing, or
  another cgroup's `memory.current` growing, in the same window our classes get evicted. With
  each node in its own cgroup, per-cgroup `memory.pressure` separates who is *suffering* from
  who is *growing*.

One process's anon allocation and another node's cache warmup are indistinguishable at the
single-eviction level, but over a sweep interval the three-way correlation is usually
unambiguous — and it is exactly the join the dashboard's context panels + mmapviz per-class
signals are designed to make visible on one screen.

**Relevance:** dashboard context. `MemAvailable` and PSI explain *why* eviction/refault spikes
happen when they do; per-cgroup `memory.stat file` is a good cross-check that per-class
`pagecache_resident_bytes` sums to something sane. On multi-node hosts all nodes compete for one
global cache — mmapviz's `datadir` label is what splits that truth per node.

## 6. Metric ↔ mechanism map

| mmapviz metric | Mechanism underneath | How to read it |
|---|---|---|
| `pagecache_file_bytes` | `fstat` | denominator per class |
| `pagecache_resident_bytes` | cachestat `nr_cache` (page cache per inode) | true, process-independent cache footprint, incl. readahead and other processes |
| `pagecache_dirty_bytes` | dirty page flag | written-but-not-flushed data (MDBX commits, snapshot builds) |
| `pagecache_writeback_bytes` | pages with IO in flight | flush pressure (msync/fsync/flushers) |
| `pagecache_evicted_bytes` | shadow entries | how much of the class reclaim pushed out |
| `pagecache_recently_evicted_bytes` | refault-distance on shadows | **thrash**: evicted data that is still part of the working set |
| `pagecache_fill_bytes_total` (`--trace.io`) | `mm_filemap_add_to_page_cache` (bytes via folio `order`) | physical read bandwidth per class |
| `pagecache_evict_bytes_total` (`--trace.io`) | `mm_filemap_delete_from_page_cache` | churn rate per class |
| one-shot `--heatmap` buckets | `mincore` per-4KiB bitmap | residency locality inside one file |
| `mem_rss`/`mem_pss` (existing) | smaps | process view; context only |
| majflt panel (existing) | getrusage | fault-latency exposure per process |
| host context: `MemAvailable`, PSI, `pgscan_kswapd`/`pgscan_direct`, `workingset_refault_file` | meminfo, PSI, vmstat | is the host under pressure; background vs stall reclaim; global refault rate (§5) |

## 7. Common misreadings

- **"RSS is huge → leak."** RSS is mostly evictable shared file pages here. Look at
  `pagecache_resident_bytes` by class and `mem_pss` before concluding anything.
- **"Free memory is almost zero."** By design. `MemAvailable` and PSI are the health signals.
- **"I dropped caches and RSS fell — fixed!"** You converted cache into a refault storm; watch
  fills spike. Nothing was leaking.
- **"The file is 100% resident but we still see disk IO."** Writeback is IO too (check
  `pagecache_dirty/writeback_bytes`), or pages are cycling between samples (check
  `recently_evicted` and, with `--trace.io`, fill vs evict rates).
- **"Another process ate our cache — can we prove it?"** Not per page (evictions carry no
  cause), but the three-way correlation in §5 — our classes' `recently_evicted`+fills up, host
  `MemAvailable` down / `pgscan_*` up, neighbor's RSS or cgroup `memory.current` up — is usually
  unambiguous.
- **"smaps and mmapviz disagree."** They measure different things (per-process PTEs vs per-inode
  cache) and both are right — see §4.
- **"VSZ is 20 TB!"** MDBX geometry reservation. Address space is free; ignore VSZ.
