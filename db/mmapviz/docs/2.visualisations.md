# mmapviz visualisation: own store, own UI — with Grafana for correlation and alerts

Answers `1.requirements.md` (the five core questions of its §2: per-file residency at any time,
per-region residency, top IO users, *why* the IO happened, and what it all looked like when
block N executed or a merge/collation/prune/unwind ran); `3.design.md` §6.4 defines the store
this doc's UI reads, and its §8 summarizes the Grafana remainder.

The "over time" clause of the requirements is the forcing function. Per-file and per-region fidelity **with history**
cannot live in Prometheus (§3), and a stateless UI cannot show it. So the sidecar persists every
sweep into its own local store (`3.design.md` §6.4) and serves a time-aware UI on top.

**Verdict:**

1. **The mmapviz UI (over the local store) is the primary surface** for all cache questions:
   current state, history, per-file trends, within-file regions over time, per-consumer IO.
2. **Grafana keeps exactly two jobs**: correlating the class-level rollups with every other node
   metric (exec latency, `db_pgops`, `process_io`…), and alerting. The sidecar keeps exporting
   the class rollups to Prometheus — they are computed for the store anyway — and the Grafana
   dashboard uses **only native panels** (a pleasant consequence: no Infinity datasource, no
   paid treemap plugin, no plugin story at all).
3. CLI strips stay for SSH-only boxes; `--json` snapshot export stays as the notebook/automation
   escape hatch (the store also exports its history as JSON for offline analysis).

## 1. Workflows the UI must serve

- **Operator glance**: is cache healthy now; headroom; thrash trend. (Also mirrored in Grafana
  for the fleet view.)
- **Incident drill-down with time travel**: "node latency spiked at 14:32 — what changed in the
  cache?" → scrub to 14:32 — or scrub *by block*: "what did the layout look like while block
  21 executed?" (FR6) — see which classes/files lost residency, which gained fills, which
  consumer caused them, and which *regions* of which files churned. First question the overlay
  answers: was that burst block execution, an unwind/re-exec episode, or a merge/collation/prune
  running in the background?
- **Release / config A/B**: pick two time points (or two nodes), diff residency and IO by class
  → file → region. First-class in the UI (two-point diff), no notebook required for the common
  case.

## 2. Chart grammar: question → chart → home

Vocabulary: a **class** is one value of the metric label tuple `{datadir, sub, name, ext, tier}`
(`3.design.md` §6.1) — e.g. all frozen `accounts` `.kv` files are one class; ~10k files collapse
into low hundreds of classes. Grafana only ever receives **class-level aggregates** (the
rollups); per-file, per-region, per-consumer, and per-episode fidelity is UI-only. Rows marked
"Grafana at class level" mean exactly that: the same signal summed per class — losing the
drill-down but gaining what only Grafana has (fleet variables, months of retention, alert
rules).

| Question | Chart | Home |
|---|---|---|
| Cache composition now & over time | stacked area by class | UI (uPlot) + Grafana (native, for correlation) |
| Which classes thrash / do IO | rate lines; alert rules | Grafana (alerting) + UI |
| Whole datadir at a glance | **treemap** (area = size, colour = resident %, thrash toggle) | UI (canvas) |
| Datadir over time | treemap + **time scrubber** (render any stored sweep) | UI |
| One class across its step/block ranges | **ordered segment strip** (x = range, colour = resident %) | UI |
| Class ranges over time | **time × step-line heatmap**: y = the class's step/block number line (the stable axis), x = time; each file paints its `[from,to)` interval, so merges show as visible **seams** where the partitioning changes (FR11) | UI |
| Inside one file | offset strip; **time × offset heatmap** from stored strips | UI (+ CLI strip) |
| Per-file history | resident/dirty/fills lines per file | UI (uPlot) |
| Top IO users | top files by fill bytes over a window; per-file **consumer breakdown** (which process role reads it) | UI |
| What changed between T1 and T2 | **two-point diff**: Δresident/Δfills by class → file → region | UI |
| State when block N executed | scrubber accepts a block number; block labels on every time axis (FR6) | UI |
| Execution IO vs background-job IO | **merge/collation/prune event spans** overlaid on fill/evict charts; click a span → its sources' sequential reads, destination writeback, the collation `mdbx.dat` scan, or prune's `mdbx.dat` dirty/writeback burst (FR6/FR7) | UI |
| Cost of an unwind | **unwind/re-exec episode spans** (depth, duration); click → rollback-phase `mdbx.dat` history reads + state-revert writeback, then re-exec fills/refaults vs the steady baseline — re-exec *should* be cache-served, so deviation = avoidable IO (FR6/FR7) | UI |
| Why did this IO happen | fills split **warmup / refault / steady / background-job / deleted** per class/file (FR7/FR11); consumer breakdown; optional `kvmetrics` logical-reads overlay | UI (+ Grafana at class level) |
| Is seeding polluting the cache? | torrent upload/download rate overlaid on fills and residency of `tier=frozen` classes — cold segments warming while hot classes evict, tracking peer demand; with `--trace.io`, fills carry the access-mechanism tag (mmap fault vs `read()`), pinning seeding per file even with the embedded downloader (FR6g/FR7) | UI |
| Is devp2p serving causing IO? | devp2p egress rate overlaid on fills for blocks/receipt classes; the time×offset heatmap's historical scatter is the visual fingerprint; standalone rpcdaemon separates by consumer role (FR6h/FR7) | UI |
| Are neighbors squeezing us? | host pressure lines (`MemAvailable`, PSI, `pgscan_*`) + opt-in neighbor-cgroup `memory.current`/`pressure` overlaid on our eviction/refault charts and job/episode spans (FR6f) — the externalcl case: CL catch-up vs our exec refaults on one axis | UI (+ Grafana context) |
| Correlation with node behaviour | new class panels beside `db_pgops`, `process_io`, majflt, latency | Grafana |
| Fleet overview / alert routing | class rollups per host/datadir | Grafana |

Cross-cutting: IEC byte units; one fixed class→colour palette shared by UI and dashboard
(defined once in `db/mmapviz`); no pie charts.

## 3. Why Prometheus/Grafana can't hold the primary dataset

- **Cardinality with history**: 5–10k files × 6–8 gauges × datadirs ≈ 10⁵ series per host,
  churning on every merge — hostile to any TSDB, and still an order of magnitude short of the
  requirement once offset strips enter (10k files × O(100) buckets). A purpose-built store
  ingests this trivially because it exploits structure a generic TSDB can't assume: strips are
  spatially coherent (RLE) and temporally stable (write-on-change) — see `3.design.md` §6.4 for
  the volume math (~tens of MB/day).
- **Axis semantics**: Grafana's heatmap is time × value-buckets; our heat views are time ×
  *position* (offset, range index). The UI renders these natively on canvas.
- **Treemap paywall**: the Grafana treemap panel (`grafana/grafana-treemap-panel` v2.x) is a
  paid marketplace plugin — unacceptable as a core-workflow dependency for the in-repo stack.
  Owning the UI makes the point moot (a squarified treemap is ~60 lines of canvas code).
- **Query shapes**: scrubbing, two-point diffs, and "top movers between T1 and T2" are awkward
  PromQL and natural store queries.

What Grafana irreplaceably keeps: months of class-level history next to every node metric,
fleet-wide variables, and the alerting pipeline. That's why the rollup export stays.

## 4. Storage engine analysis (decision recorded in `3.design.md` §6.4: MDBX)

| Option | Verdict | Reasoning |
|---|---|---|
| **MDBX** (in-house) | **chosen** | zero new deps; the team's deepest expertise; single-writer append pattern fits; range scans cover every UI query shape; wipe-and-restart doctrine keeps it simple |
| SQLite | rejected | new dep (cgo or modernc) for SQL we don't need — query shapes are fixed |
| DuckDB embedded | rejected | superb analytics, heavy cgo dep; belongs in the *offline* notebook path reading our JSON/parquet exports |
| Parquet chunk files + own reader | not v1 | attractive erigon-shaped evolution (db → immutable frozen chunks) if retention ever grows to months; revisit then |
| Prometheus TSDB / VictoriaMetrics as library | rejected | built for labeled scalar series; strips don't fit; cardinality churn is their weak spot; embedding is operationally opaque |
| Plain JSONL log + in-memory index | rejected | simplest write path but query latency and retention management end up reimplementing a store badly |

## 5. UI spec

### Tech stack

**Server side**: nothing new — Go `net/http` handlers on the sidecar's existing listener,
`/api/v1/*` JSON over the store, static assets via `go:embed`. gzip on JSON responses; strip
data is passed to the client **still RLE-encoded** (decoding is ~30 lines of JS) so heat views
stay small on the wire.

**Client side — two layers, both build-free:**

- *Viz layer (imperative)*: `<canvas>` + one vendored single-file library, **uPlot** (MIT,
  ~45 KB, the fastest small time-series lib; drag-zoom and multi-chart cursor sync built in).
  Treemap, segment strips, and the time×offset/time×step-line heat views are hand-rolled canvas
  — no framework renders those, and canvas is imperative regardless, so frameworks buy nothing
  here.
- *Chrome layer (declarative)*: **preact + htm**, vendored as two more single files (~13 KB, no
  JSX, no compile). Toolbars, time picker, legends, tables, the diff panels — the parts where
  hand-rolled DOM/state code rots as interactions multiply (linked cursors, follow mode,
  selections, diff state) — get declarative components; the canvases mount inside them and keep
  drawing imperatively. Given the Grafana-grade interactivity required below, this is a day-one
  choice, not an escape hatch.

Hard invariant unchanged: **no npm, no node, no bundler, no build step** — the repo has zero
frontend toolchain and this project doesn't justify one (CI, lockfiles, supply chain). Rejected:
React+Vite (build toolchain; Preact *is* the React API at a tenth the size), Svelte/Solid
(compilers — great DX, violates the invariant, marginal gain at this scale), ECharts/Plotly
(~1–3.5 MB payloads with built-in zoom we don't need — uPlot outperforms them on dense series
and none of them draw our custom views), Alpine/petite-vue (too weak for this state graph),
htmx/server-rendering (zoom/scrub must not round-trip), Go→WASM (payload and complexity for a
30-line RLE decoder).

### Interactivity & liveness

- **Live/follow mode**: the time axis follows "now", pausing on any user interaction (Grafana's
  refresh behavior). Honest freshness = the collection cadences: fill/evict counters and
  activity annotations ~15–30 s fresh; residency/strips at sweep cadence (1–5 min). This is a
  monitoring UI over minute-cadence data, not a tick feed — "real time" means new points appear
  as they land. v1 uses `since=`-cursor delta polling (tiny responses); an SSE endpoint
  (`/api/v1/events`, plain HTTP so it survives tunnels/proxies) is the later upgrade that makes
  live mode push-driven instead of poll-driven.
- **Time navigation, Grafana-grade**: drag-select to zoom on any chart, wheel zoom + drag pan,
  double-click to reset, one **shared time-window store** that every view (uPlot charts *and*
  canvas heat views) subscribes to — zoom anywhere, everything moves; synced crosshairs across
  stacked charts (uPlot sync groups; the canvas views subscribe to the same cursor bus).
- **Level-of-detail**: queries carry `from/to/step` like a Prometheus range query; the server
  downsamples wide windows, and buckets return **min/mean/max** so a one-sweep thrash spike
  survives a 14-day zoom-out instead of averaging away. Narrow windows return raw sweeps. The
  client keeps an LRU of fetched windows, so zoom-out → zoom-in re-renders from cache with zero
  network.
- **Shareable state**: the full view state (view, datadir, window or block anchor, selections)
  lives in the URL hash — paste a link to a colleague (through their own tunnel) and they land
  on the same picture.

Payload budget: ≤ ~200 KB total transfer, cold. Code budget: ~4–5k lines of our JS/HTML
(vendored libs excluded); past that, features move to Grafana or get cut.

### Remote access (server-side sidecar, laptop browser)

Designed for exactly this: the UI is same-origin, relative-URL only (works behind a port-forward
or a reverse-proxy path prefix), self-contained (no CDN — it renders on an air-gapped link), and
**latency-tolerant**: the client fetches a time *window* of data and scrubbing/diffing within it
is pure client-side rendering — zero round-trips until the window changes. Access patterns, in
order of preference:

1. **SSH tunnel** (default, zero setup): `ssh -L 6070:localhost:6070 server` →
   `http://localhost:6070/ui`. Encrypted, no public exposure, works today.
2. **VPN overlay** (tailscale/wireguard) for persistent multi-host access.
3. **Internet exposure only behind a TLS + auth reverse proxy** (caddy/nginx basic-auth): the
   listener itself deliberately ships **no auth** and binds loopback by default — putting it on
   `0.0.0.0` raw would publish the node's access patterns and datadir layout. The pages are
   served with a strict same-origin CSP either way (cheap hardening, and everything is
   self-contained anyway).

### Future: hosted UI on our domain, many sidecars plugging in

An anticipated evolution, not a v1 deliverable — but the v1 contract is shaped so it needs no
rework:

- **The UI is a static bundle talking only to versioned JSON APIs.** Hosting that same bundle on
  our domain requires zero changes to it — only pointing it at sidecars. To keep that true, all
  client fetches go through one `api(base, path)` helper: `base` defaults to same-origin
  (today's mode) and is configurable (hosted mode).
- **`/api/v1/meta`** (shipped in v1): instance identity — host label, sidecar version, datadirs,
  retention, capabilities (`--trace.io` on?, annotations on?). The UI uses it today for
  discovery and feature-detection; a hosted hub uses it tomorrow for registration and for
  tolerating mixed sidecar versions (v1 API evolves additively only).
- **Source becomes a dimension.** The client data layer keys everything by `(source, datadir)`
  from day one — single-source today, N sidecars later, no remodel.
- **Connection topology — decided when actualized, both kept viable:**
  (a) *inbound*: hosted static UI fetches sidecars directly — needs the reserved
  `--serve.cors-origins` allowlist (off by default), per-sidecar bearer tokens, and TLS in
  front of each sidecar;
  (b) *outbound hub*: sidecars dial out and register with the hosted service, which proxies
  queries — the `erigon support` / diagnostics.erigon.io pattern this org already runs. Outbound
  suits the fleet reality better (no inbound ports, works behind NAT), at the cost of running a
  hub service. Either way the sidecar's `/api/v1` contract is the stable interface.
- **Auth escalates in hosted mode**: the no-auth-loopback stance is v1-local-only; anything
  hosted requires tokens + TLS as a hard precondition.
- **OTLP as a candidate fleet transport**: in the hosted phase, an optional OTLP exporter for
  the aggregate layer (class rollups + activity spans — never strips/per-file detail, which
  stay behind `/api/v1`) could feed existing org OTel/ClickHouse pipelines instead of a bespoke
  hub protocol. Explicitly out of v1 (`1.requirements.md` §5); adapter-at-the-edge only.

### Views & data plane

- **Global time control**: live mode (poll 10–30 s) / time-range picker / scrubber over stored
  sweeps; every view is a function of (datadir, time | time-range). With activity annotations
  (`3.design.md` §6.4) the scrubber also accepts a **block number** (jumping to its execution
  interval, plural on unwinds) and every time axis carries block labels; merge, collation, and
  prune event spans plus unwind/re-exec episodes (`3.design.md` §6.4 — the first two
  walk-derived, the rest metrics-derived) are drawn on the same axes. Scrubbing to the past renders files that have since been merged away,
  exactly as they were.
- **Views (tabs)**:
  - **Overview**: treemap (resident %/thrash toggle) + composition stacked area + top movers in
    the selected window.
  - **Classes**: segment strip per class now; click → the time × step-line heatmap, with merge
    seams and merge-event markers drawn in (FR11).
  - **File**: offset strip now; time × offset heatmap; scalar history lines; consumer breakdown
    (fill bytes by process role).
  - **Diff**: pick T1/T2 → sorted Δ tables and strip diffs, class → file → region.
- **Data plane**: versioned JSON APIs over the store — `/api/v1/meta` (instance identity +
  capabilities), `/api/v1/files`, `/sweeps`, `/strips`, `/rollups`, `/consumers`, plus existing
  `/debug/pagecache` (kept as the simple "now" snapshot for CLI/scripts). All read-only; same
  operator-only listener; all queries are windowed (time-range parameters) so the client can
  scrub locally within a fetched window; `from/to/step` downsampling (min/mean/max buckets) and
  `since=` cursors for live deltas; optional SSE at `/api/v1/events`. v1 evolves additively only
  — this API is the stable contract a future hosted UI/hub builds on.
- Palette shared with Grafana; dark/light via `prefers-color-scheme`.
- Explicit non-goals: auth, editing, cross-host aggregation (per-host UI; the fleet view is
  Grafana's job), mobile polish.

## 6. What remains in Grafana (`pagecache.json`, all native panels)

- Health row: stacked resident-by-class, `MemAvailable` + PSI, residency-ratio bar gauge.
- Thrash/IO row: `recently_evicted` by class; fill vs evict bytes/s; dirty/writeback; majflt and
  `process_io` overlays.
- Links row: text panel deep-linking to `${mmapviz_url}/ui` per datadir (the drill-down handoff).
- Alert rules: sustained `recently_evicted > X%` of class size; sustained fills on
  `tier=frozen`; with the store on, sustained `kind="refault"` fills on any class (the
  avoidable-IO alert, `3.design.md` §6.4).
- Cadence discipline: sampler-fed gauge windows ≥ 2× sweep interval (checked in `4.testing.md`
  §6); panel descriptions state the cadence.

## 7. Usability acceptance (ties into `4.testing.md`)

On the pressure-demo scenario, a newcomer must answer, unaided: from Grafana — "which class is
being squeezed?"; after one click into the UI — "which files, and which parts of them?"; and
with the scrubber — "when did it start, and what did the treemap look like before?". Given a
block number from a bug report, they must reach its execution moment in one action. During the
`--trace.io` cross-check they must be able to name the top consumer of a named file and say
which share of its fills were refaults (avoidable) vs warmup. Any view
that needs explanation beyond its own annotations gets redesigned or cut.

## 8. Open questions

- Retention defaults (proposal: 14 d full fidelity, cap 2 GiB, oldest-first prune) — tune on the
  archive-node soak.
- Store dir default (`<datadir-sibling>/mmapviz-store` vs XDG path) — operator ergonomics call.
- Downsampling beyond retention (keep hourly rollups for 90 d?) — decide after real usage; the
  parquet-chunk evolution (§4) is the natural home if wanted.
- `mmapviz_url` resolution on multi-host fleets (dashboard variable vs reverse proxy) — operator
  decision, documented, not solved in code.
