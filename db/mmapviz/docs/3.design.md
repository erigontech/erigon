# mmapviz design: per-file residency, per-file IO, history, visualisation

## 0. Objective

Erigon's working set is almost entirely mmap-backed: every snapshot/state file (`.seg`, `.kv`, `.bt`,
`.kvi`, `.kvei`, `.v`, `.vi`, `.ef`, `.efi`, `.idx`) plus every MDBX environment (`mdbx.dat`) is read
through the page cache, not through heap buffers. Today we have process-level visibility only
(`mem_rss`/`mem_pss` from `diagnostics/mem`, `db_pgops`, `process_io`, getrusage major faults). We
cannot answer, for a long-running node:

1. **Footprint** — how many bytes of page cache does each file (and each file *class* — domain vs
   history vs inverted index vs block segments vs MDBX) hold right now, and how does that evolve?
2. **IO attribution** — which files cause the disk reads (page-cache fills), which files thrash
   (eviction churn under memory pressure), which files generate writeback?
3. **Locality** — *which regions* of a given file are resident/hot (e.g. is a `.bt` fully cached
   while only the tail steps of `.ef` files are)?
4. **Correlation** — join the above with existing metrics (sync stage, RPC load, `db_pgops`,
   `process_io`) on one screen, *including node and peer activity*: at time T the node executed
   block N, ran a background job (merge/collation/prune), or served peer demand
   (seeding/devp2p) — what did the cache/IO layout look like (FR6).
5. **Explanation** — separate avoidable IO from necessary IO: warmup vs refault/thrash vs
   writeback, and "code asked too much" vs "cache couldn't hold it" (FR7).

Non-goals (for now): page-cache *control* (madvise/mlock policy changes), Windows/macOS parity
(stubs only), per-query cache-hit accounting inside domain reads (revisited as an optional phase —
see §7).

Requirements (the why, the FR/NFR numbering used below, and success criteria) live in
`1.requirements.md`; this doc is the technical response. It surveys what the kernel and existing
tools offer, reports measurements taken on a fleet-representative host, and proposes a phased
design. The OS mechanics it relies on (RSS vs PSS vs page cache, mmap, faults, reclaim/shadow
entries) are explained in the companion `0.background.md`. TL;DR of the recommendation:

- **Build one sidecar, `mmapviz`** — a new top-level `erigon mmapviz` command run as its own
  process, zero changes to the node: a `cachestat(2)`-based sampler (kernel ≥ 6.5) exporting
  per-file-class gauges on its own Prometheus listener, a `/debug/pagecache` JSON endpoint plus a
  one-shot CLI mode for per-file drill-down and offset heatmaps, and — when granted
  `CAP_BPF`+`CAP_PERFMON` — an eBPF tier for true per-file IO attribution (fills/evictions/
  writeback per inode via tracepoints). Unprivileged it delivers everything except the IO
  counters; one instance covers every node on a host.
- **Keep full-fidelity history locally**: the sidecar persists every sweep — per-file scalars,
  compressed offset strips, per-file/per-consumer IO deltas, and the activity/pressure streams
  (chain position, job/episode spans, host/neighbor/torrent/devp2p) — into its own small MDBX
  store with bounded retention (§6.4), and serves a time-aware UI over it
  (`2.visualisations.md`).
  Prometheus still receives the class-level rollups for fleet correlation and alerting.
- **Do not instrument the domain read/write paths** for footprint/IO purposes — the kernel already
  attributes both better than we can from userspace, at zero cost to hot loops (§7).
- **Visualize primarily in mmapviz's own `/ui`** (time-aware, over the local store); Grafana
  keeps class-rollup correlation and alerting via one extra scrape target on the existing
  dockerized stack, with native panels only. Full analysis and chart grammar:
  `2.visualisations.md`.

## 1. What erigon maps (inventory)

Two mmap libraries are in play — erigon's own `common/mmap` (thin wrapper over `x/sys/unix`) and
`github.com/edsrzf/mmap-go` — plus MDBX's internal map:

| Consumer | Files | mmap site | Path/size retained | Default advice |
|---|---|---|---|---|
| `seg.Decompressor` | `.seg .kv .v .ef` | `db/seg/decompress.go:248` (common/mmap) | yes | `MADV_RANDOM` baseline at map (`common/mmap/mmap_unix.go:61`), then `MadvNormal().DisableReadAhead()` at open (refcounted); separate transient `MADV_SEQUENTIAL` view for bulk scans (`OpenSequentialView`, `decompress.go:720`) |
| `recsplit.Index` | `.idx .efi .vi .kvi` | `db/recsplit/index.go:143` (common/mmap) | yes | `MadvSequential().DisableReadAhead()` at init; embedded existence-filter region has `ForceExistenceFilter{WillNeed,Normal,Random,InRAM}` hooks (`index.go:304-344`) |

| transient builders | ETL tmp (`db/etl/dataprovider.go:155`, SEQUENTIAL), recsplit offset tmp (`recsplit.go:882`), eliasfano32 RW (`elias_fano.go:150`), fusefilter writer | — | short-lived build-time maps |

| torrent downloader | **not mmap** — file storage with part files (`db/downloader/downloader.go:1446`) | — | — | its seeding reads/verification still populate the same page-cache inodes |

Caplin block/state snapshots go through the shared Decompressor/Index path, so they are covered by
the first two rows; likewise polygon/heimdall segments.

Facts that shape the design:

- **There is no central registry of live mappings** — `common/mmap` is stateless. The de-facto
  registries are the state aggregator's dirty-file sets (`FilesItem`,
  `db/state/dirty_files.go:118` — groups the `.kv`+accessor+`.bt`+`.kvei` of one step range,
  knows size and `frozen`) and `BaseRoSnapshots.dirty` → `DirtySegment`
  (`db/snapshotsync/snapshots.go:200`). The public `kv.VisibleFile` interface exposes
  path/ranges but not size/frozen.
- **Name→semantics parsers already exist** and work from the filename alone:
  `snaptype.ParseFileName` (`db/snaptype/files.go:123`) for the block form
  (`v1.0-000000-000500-headers.seg`) and the `E3SnapSchema.Parse` regex
  (`db/state/snap_schema.go:387`) for the dotted state form (`v1.0-accounts.0-1024.kv`).
  Extension catalogs: `AllV3Extensions` = `.kv .v .ef .kvei .vi .efi .bt .kvi` (+ seedable `.ap`),
  `AllV2Extensions` = `.seg .idx .txt .toml` (`db/snaptype/files.go:358-370`).
- **Readahead is deliberately suppressed almost everywhere** (`MADV_RANDOM` baseline, dbg knob
  `SNAPSHOT_MADV_RND` default true; MDBX `NoReadahead`). Consequence for observability:
  page-cache fills ≈ demand faults at mostly single-page granularity, so per-file fill counts
  track real access closely and offset heatmaps come out sharp.
- **Logical read attribution already exists**: `db/state/kvmetrics` exports
  `kv_read_count{source,domain,op}` / `kv_read_duration_ns` (source ∈
  exec|commitment|warmup|rpc|engine, op ∈ cache|db|file|…) plus a read-amplification ratio,
  gated by `KV_READ_METRICS` (default off, `common/dbg/experiments.go:74`). It attributes reads
  to *code paths*, not to physical files or disk IO — exactly complementary to this design (§7).
- MDBX already exports GC major-fault counters (`DbGcWorkMajflt`/`DbGcSelfMajflt`,
  `db/kv/kv_interface.go:766`), and devs already probe residency by hand — see the vmtouch
  benchmarking notes in `db/state/inverted_index.go:1173` asking whether `.ef`/`.efi` stay
  resident. This doc productizes those questions.

## 2. Semantics: four different "how much memory" questions

These get conflated constantly (including in "erigon eats all my RAM" user reports). The design
must expose them as distinct metrics (full primer: `0.background.md`; this table is the
operational summary):

| Metric | Meaning | Where it comes from |
|---|---|---|
| **mapped bytes** | length of active `mmap` regions per file | `/proc/self/maps`, or our own registries |
| **process-mapped resident (Rss/Pss per VMA)** | pages of the mapping currently present in *erigon's page tables*; what `top` shows as RSS | `/proc/self/smaps`, `pmap -X` |
| **page-cache resident** | pages of the *file* in the kernel page cache, regardless of who faulted them (includes readahead, other processes, pages reclaimed from our page tables but still cached) | `mincore(2)`, `cachestat(2)` |
| **hot / recently used** | pages actually accessed in a recent window | access-bit sampling (DAMON, `clear_refs`), eviction/refault signals |

Key consequences:

- Page cache is **global**: a separate process (CLI, sidecar) can measure residency and IO of
  erigon's files *without touching the erigon process at all*. This is what makes the
  all-in-sidecar architecture (§6) possible and safe.
- Per-VMA Rss (smaps) requires walking erigon's page tables while holding its `mmap_lock` for
  read — on a multi-TB mapping this takes seconds of kernel time per scan and can contend with
  map/unmap (file open/close at merges). Fine ad-hoc (`pmap -X`), wrong as a periodic scraper.
- `cachestat`/`mincore` measure the file mapping (inode), take no erigon lock, and their cost
  scales with *resident* pages, not file size (measured below) — cold TBs are almost free to scan.

## 3. Kernel primitives (survey + measurements)

Measured on a fleet-representative host: Ubuntu, kernel `6.8.0-85-generic`, 125 GiB RAM, ext4 on
md RAID. Probe source: cachestat/mincore sweep in 1 GiB chunks (see §12).

| Primitive | Gives | Cost (measured) | Caveats |
|---|---|---|---|
| `cachestat(2)` (kernel ≥ 6.5, `x/sys/unix.Cachestat`, already at v0.46.0 in go.mod) | per fd+range: `nr_cache`, `nr_dirty`, `nr_writeback`, `nr_evicted`, `nr_recently_evicted` | **cold file ≈ free** (4 GiB fully-uncached mdbx.dat: 2.4 µs); warm: ~123–148 ns per *resident* page (4 GiB fully cached: ~130–155 ms) | fd-based, no mmap needed, no target-process locks; hugetlbfs unsupported; per-range aggregate only (no bitmap) |
| `mincore(2)` | per-4KiB-page residency bitmap of a mapping | ~45 ns/page cold, ~130–145 ns/page warm (walks *every* page) | must mmap the file in the caller; since kernel 5.2 truthful only if caller may write the file (owner) — fine for same-user tooling; the bitmap is what offset heatmaps need |
| `/proc/pid/smaps`, `pmap -X`, `smaps_rollup` | per-VMA Rss/Pss/etc with file path | page-table walk, seconds on TB mappings; holds target `mmap_lock` (read) | already sampled process-wide by `diagnostics/mem` via gopsutil; per-file periodic use discouraged |
| tracepoint `filemap:mm_filemap_add_to_page_cache` / `mm_filemap_delete_from_page_cache` | every page-cache fill/removal with `s_dev`, `i_ino`, `index`, `order` (verified present on 6.8) | in-kernel BPF map aggregation ~O(100 ns)/event; idle cost zero | needs root / CAP_BPF+CAP_PERFMON → sidecar, not in-process; `order` lets us count exact bytes (`4096<<order`) |
| tracepoints `writeback:writeback_dirty_folio`, `wbc_writepage` | dirtied/written-back folios with inode | same as above | write-side attribution; sampler's `nr_dirty`/`nr_writeback` covers most needs without eBPF |
| `/proc/pid/io`, getrusage majflt | process-level physical IO / major faults | negligible | already exported (`process_io`, majflt panels); no per-file split |
| cgroup v2 `memory.stat` (`file`, `active_file`, `inactive_file`), `io.stat` | cgroup-level page cache & IO | negligible | good top-line sanity check if erigon runs in its own cgroup |
| DAMON (`damo` heatmaps) | temporal access heatmaps over address space | low (adaptive sampling) | **not available on stock Ubuntu 6.8** (`CONFIG_DAMON` unset) — custom-kernel deep dives only |
| `/proc/pid/clear_refs` + `Referenced:` | crude "accessed since last clear" | smaps-scan cost ×2 | destructive to kernel aging hints; superseded by eviction signals; not proposed |

Empirical demo of per-file IO attribution (bpftrace one-liner, 10 s window, while reading 400 MiB
of a cold `mdbx.dat` with `dd`):

```
# bpftrace -e 'tracepoint:filemap:mm_filemap_add_to_page_cache { @fills[args->s_dev, args->i_ino] = count(); }'
@fills[9437187, 125840822]: 103936      <- the mdbx.dat inode: 400MiB/4KiB = 102400 pages + readahead
@fills[9437187, 128385170]: 8184        <- background activity of other nodes on the host
...
```

Attribution works, is exact, and costs nothing when idle. The `nr_evicted` /
`nr_recently_evicted` fields of `cachestat` come from shadow entries; per the man page, "a page is
considered recently evicted if its reentry into the cache would indicate active usage under memory
pressure" — i.e. a direct per-file **thrash signal** with no eBPF and no privileges.

## 4. Existing tools (and why none closes the gap)

| Tool | What it does | Verdict for us |
|---|---|---|
| `vmtouch` (installed on our hosts) | mincore-based residency per file/dir, can also touch/lock | great ad-hoc CLI; no daemon/metrics mode, no IO, no erigon semantics |
| `pcstat` (tobert), `pgcacher` (rfyiamcool), `hcache` | Go tools, mincore per file; pgcacher: top-N, per-process fd scan, parallel workers | same as vmtouch but scriptable/JSON; `pgcacher --top` is the best "what's in my page cache" snapshot today |
| `fincore` (util-linux) | residency per file | not installed on our hosts by default; same niche |
| bcc `cachetop`/`cachestat` | system/process-wide cache hit ratios | no per-file breakdown |
| bcc `filetop`, `biotop`, `biosnoop` | per-file VFS reads / per-process block IO | `filetop` misses mmap faults (VFS read path only); block tools lack file attribution |
| bpftrace (installed) | ad-hoc tracepoint aggregation | the §3 demo; basis of the cookbook and the sidecar |
| Cloudflare `ebpf_exporter` | config-driven BPF → Prometheus | could host our tracepoint programs, but cannot resolve inode→snapshot-file-name; we need our own tiny resolver anyway |
| node_exporter / process-exporter | global `Cached`, per-process RSS/IO | context panels only |
| DAMON + `damo` | address-space access heatmaps over time | blocked on kernel config (§3) |

Searches for a maintained "per-file page cache Prometheus exporter" came up empty — this niche is
genuinely unfilled, which is why the proposal builds a thin one rather than importing something.

## 5. Cookbook — what works today with zero code

Immediately usable on any node (all read-only; the first three need no privileges when run as the
erigon user):

```bash
# 1. Residency snapshot of a datadir subtree (per file + total)
vmtouch -f ~/erigon/datadir/snapshots            # summary
vmtouch -v ~/erigon/datadir/snapshots/*.kv       # per-file, with coarse resident-range map

# 2. Top cached files on the host / for a process (go install github.com/rfyiamcool/pgcacher@latest)
pgcacher --top 30
pgcacher --pid $(pidof erigon)

# 3. Per-mapping RSS as erigon's page tables see it (ad-hoc only — seconds of kernel time,
#    holds erigon's mmap_lock for read while scanning)
pmap -X $(pidof erigon) | sort -k3 -n | tail -40

# 4. Which files fill the page cache right now (root; exact bytes incl. readahead)
bpftrace -e 'tracepoint:filemap:mm_filemap_add_to_page_cache
             { @fill_bytes[args->s_dev, args->i_ino] = sum(4096 * (1 << args->order)); }'
# ...and which get evicted
bpftrace -e 'tracepoint:filemap:mm_filemap_delete_from_page_cache
             { @evict_bytes[args->s_dev, args->i_ino] = sum(4096 * (1 << args->order)); }'
# resolve inodes afterwards:
find ~/erigon/datadir -type f -printf '%i %p\n' | sort > /tmp/inodes.txt

# 5. Writeback attribution (root)
bpftrace -e 'tracepoint:writeback:writeback_dirty_folio { @dirtied[args->ino] = count(); }'
```

These answer one-off questions but don't give continuous per-class time series, don't survive in
dashboards, and need manual inode→file joins — hence the design below.

## 6. Design

**One sidecar program — `mmapviz`** — with four capabilities (components A–D below), all
Linux-only. The node binary and its hot paths run zero new code. Shape: a new top-level command
of the main binary — `erigon mmapviz` one-shot for ad-hoc questions, `--serve` for the
long-running exporter — so the name parsers and class labels always match the deployed datadir
layout. The command layer is deliberately slim: parse flags, build a config, hand off to
**`db/mmapviz`**, where all enumeration/classification/sweep/serving logic lives. That package
sits naturally under `db/` because everything it depends on is already there (`datadir`,
`snaptype`, the `state` name schema, `dbcfg`).

### 6.1 Component A — page-cache sampler → Prometheus (the sidecar core)

A sampling loop that, for each configured datadir, on every tick:

1. Enumerates files by **recursively walking the datadir root** and classifying what it finds:
   snapshot-shaped names via the **existing parsers** (§1), and **every `mdbx.dat` wherever it
   appears** — labeled with its dbcfg name where the parent dir matches the catalog (chaindata,
   txpool, consensus, downloader, heimdall, polygon-bridge, caplin, diagnostics, …) and with the
   datadir-relative dir otherwise (e.g. `nodes/eth68`, `caplin/indexing`). Discovery-by-walk
   rather than a fixed dir list means new or uncataloged envs can never be silently missed
   (the devp2p `nodes/<protocol>` DBs are already outside the dbcfg catalog today). The
   `datadir.Dirs` catalog (`db/datadir/dirs.go:41`) only guides labeling. This needs zero
   changes in any mmap consumer, survives registry refactors, and also counts cache held by
   files not currently open (e.g. just-merged segments pending delete). A configured datadir
   need not be erigon's: pointing `--datadir` at a coresident CL client's directory
   (lighthouse/prysm/teku on externalcl hosts) tracks its files with ext-only labels — the
   junk-tolerant classifier guarantees graceful degradation (FR1). Dedupe by `(dev, inode)`
   — the same inode may be mapped twice by the node (Decompressor main map + transient
   sequential view) and read as plain file IO by the torrent seeder; page cache is per-inode.
   Optional later enrichment: a `visible/frozen` flag from `FilesItem`/`DirtySegment` — being
   out-of-process, that would need a small node debug endpoint exposing the visible-file list
   (deferred; range-width-derived `tier` covers the need for now).
2. For each file: `open(O_RDONLY)`, `fstat`, `unix.Cachestat` in ≤1 GiB chunks over `[0, size)`,
   close. Accumulate `{cache, dirty, writeback, evicted, recently_evicted}`.
3. Aggregates into gauges keyed by a **low-cardinality class label set**, not per file:
   `{datadir="...", sub="state|blocks|caplin|heimdall|mdbx|downloader|temp", name="accounts|storage|code|commitment|receipt|headers|bodies|transactions|<dbcfg label for mdbx>|...", ext=".kv|.bt|.kvei|.kvi|.v|.vi|.ef|.efi|.ap|.seg|.idx|.dat|other", tier="frozen|latest"}`
   with `tier` derived from the parsed range width (frozen ≙ full-width ranges). The `datadir`
   label is what lets one sidecar serve every node on a host. ~15 names × ~10 exts × 2 tiers ≈
   low hundreds of series per datadir. Per-file series are **not** exported by default (see
   Component B for per-file detail).

Metrics (all gauges, prefix `pagecache_`):

```
pagecache_file_bytes{sub,name,ext,tier}                # sum of file sizes (denominator)
pagecache_resident_bytes{...}
pagecache_dirty_bytes{...}
pagecache_writeback_bytes{...}
pagecache_evicted_bytes{...}                           # shadow-entry based
pagecache_recently_evicted_bytes{...}                  # thrash signal
pagecache_files{...}                                   # file count
mmapviz_sweep_seconds / mmapviz_sweep_age_seconds      # sidecar self-telemetry
```

Naming: measurement series keep the semantic `pagecache_` prefix — they describe the data, not
the tool, and survive any future re-hosting. Only self-telemetry carries the `mmapviz_` prefix,
and `mmapviz` is the Prometheus job/service name.

Budget control: sweep cost scales with *resident* bytes (§3), worst case ≈ RAM size. Measured
worst case ~135 ns/resident page (order-0 folios) → 100 GiB resident ≈ 3.5 s CPU per full sweep.
The sampler therefore (a) rotates: scans at most `N` files per tick so a full pass completes
within a target period (default: full pass ≤ 5 min), (b) self-tunes: if a full pass takes more
than 0.5% of one core at the current cadence, it stretches the interval and logs once, (c) yields
between chunks (it holds no locks, so this only bounds its own CPU share) — and being a separate
process, it can additionally be hard-capped from outside (systemd `CPUQuota`/cgroup). On kernels
< 6.5 (`ENOSYS`) it falls back to mapping each file read-only and running chunked `mincore`
(truthful as datadir owner, §3), or disables itself; either way it logs the degradation once.

Node flags: **none — the node is not touched.** Sidecar flags: `--datadir` (repeatable),
`--serve.addr` (default `127.0.0.1:6070` — loopback; binding wider is an explicit operator
decision, §10), `--interval`, `--cpu.budget`, plus `--trace.io` (§6.3) and
`--store.dir`/`--store.max-size`/`--node.metrics.url` (§6.4). All logic lives in `db/mmapviz`;
the `erigon mmapviz` command only parses flags and starts it (§6.2).

### 6.2 Component B — per-file drill-down: `/debug/pagecache` + `erigon mmapviz` one-shot

Same collection code, two consumers:

- **`/debug/pagecache`** (on the sidecar's own mux, beside the `/debug/metrics/prometheus` it
  serves): JSON array of per-file rows
  `{path, sub, name, ext, tier, size, resident, dirty, writeback, evicted, recently_evicted}`,
  computed on demand (rate-limited, cached for ~10 s). Sorted by resident desc.
  `/debug/pagecache?file=<glob>&buckets=1024` additionally returns an **offset heatmap**: the
  file split into `buckets` equal ranges, residency fraction per bucket — computed via `mincore`
  on a private temporary mapping (per-4KiB resolution, one pass, then munmap; a 32 GiB file at
  1024 buckets costs ~1 s worst-case and only when requested).
- **`erigon mmapviz`** (new top-level command, registered beside `snapshotCommand` in
  `cmd/utils/app/make_app.go:88`; `--json` output modeled on `seg du`): one-shot by default;
  **`--serve` turns the same command into the long-running sidecar** (sampler + the endpoints
  above). Both modes work against **any datadir, including one served by a live node**, because
  page cache is global — no attach, no locks, no effect on the node. It must *not* take the
  datadir lock or open snapshot/DB objects: it is a pure dir walk plus read-only fds and
  syscalls. One-shot output: per file-class table + optional per-file `--top N` +
  `--heatmap <file>` rendering a Unicode strip:

```
v1.0-accounts.0-1024.kv      64.0 GiB  resident 41%  dirty 0  recently-evicted 1.2 GiB
  [████▇▆▁▁▁▁▂▁▁▁▁▁▁▁▂▃▅███████▇▅▂▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▂▂▅▇██]
```

The one-shot mode covers the "quick question on a prod box" case with zero deployment; the
endpoint is the "now" snapshot API for the CLI, scripts, and the UI — per-file data never enters
Prometheus (per-file browsing lives in `/ui`, keeping the Grafana dashboard plugin-free —
`2.visualisations.md`).

### 6.3 Component C — eBPF IO attribution (the sidecar's privileged tier)

Enabled with `--trace.io` on hosts where per-file IO attribution is wanted; requires the sidecar
to run as root or with `CAP_BPF`+`CAP_PERFMON` (without them the flag refuses to start and the
unprivileged tiers keep working):

- Attaches the two `filemap` tracepoints (+ optionally `writeback_dirty_folio`), aggregates
  `sum(4096 << order)` into a BPF LRU hash keyed by `(s_dev, i_ino)` — in-kernel, ~100 ns/event,
  zero idle cost, no per-event userspace wakeups.
- Fills additionally carry an **access-mechanism tag** — fault-driven (mmap access) vs
  syscall-read-driven (`read`/`pread`; `pread` = read at an explicit offset with no shared file
  position, the natural call for serving many concurrent random piece requests over one fd —
  Go's `File.ReadAt`) — implemented with a per-task flag set/cleared on read-syscall entry/exit
  and consulted by the filemap tracepoint program (two more tracepoints, same ~100 ns class). The node reads snapshots through mmap faults while the torrent seeder
  reads them through `pread`, so this tag is what attributes seeding from *inside* the node
  process (§6.4).
- Userspace every 15 s: drains the map, resolves inodes via a `(dev,ino) → path` table built by
  walking the configured datadirs (few thousand `stat` calls, refreshed on miss and every ~10 min;
  unresolved inodes → `name="other"`, deleted-but-mapped files keep their last name), maps paths
  through the same class-labeling code as Component A, and exposes:

```
pagecache_fill_bytes_total{sub,name,ext,tier}      # physical reads into cache (incl. readahead)
pagecache_evict_bytes_total{...}                   # eviction churn
pagecache_dirtied_bytes_total{...}                 # write-side (optional)
```

- Why this lives in the sidecar and never in the node: erigon nodes run unprivileged and should
  stay that way; BPF object lifetime/failure stays isolated from the node; tracepoints are
  system-wide anyway, so one privileged sidecar observes every node (and the standalone
  downloader) on the host. `cilium/ebpf` is already an indirect dependency and the kernel ships
  BTF (`CONFIG_DEBUG_INFO_BTF=y`), so a CO-RE implementation needs no kernel headers at runtime.
  A `bpftrace`-script + textfile-collector variant is an acceptable v0.

The tier is strictly optional: the unprivileged sidecar already delivers footprint + thrash
signals; `--trace.io` adds exact read/write bandwidth per file class and per-file fill
attribution.

### 6.4 Component D — local history store (the "over time" layer)

The goal restated: which files sit in the page cache, which regions of them, and who does the IO
— **over time**, not just now. Class-level history fits Prometheus; per-file and per-region
history do not (`2.visualisations.md` §3). So `--serve` keeps its own store:

- **Engine: MDBX** (what this codebase knows best; single writer = the sweep loop; dbcfg label
  `mmapviz`). Corruption or a schema bump is handled by **wipe-and-restart**: this is
  observability data, not consensus data, so recovery is a fresh store — no migrations, no
  repair paths, drastically simpler code. Engine alternatives are analysed in
  `2.visualisations.md` §4.
- **Identity & merge lineage (FR11)**: `file_id` surrogate keyed by `(dev, ino, first_seen)`;
  every merge mints new ids. Merges do not replace files 1:1 — they **re-partition the range
  axis** (`accounts.0-64.kv` + `accounts.64-128.kv` → `accounts.0-128.kv`), so no per-range row
  is stable over time. The stable coordinate is the **step/block number line**: each file covers
  an interval on it, and time views paint per-file values across that interval
  (`2.visualisations.md` §2). Lineage — which files a new file superseded — is derived from
  range containment within a class plus appear/disappear timestamps; nothing extra to track.
  `files` rows are tombstoned (`last_seen`), never dropped before retention, so scrubbing to the
  past renders layouts as they were, including files that no longer exist.
- **Tables** (shapes, not final schema): `files` (id ↔ path, labels, first/last seen);
  `sweeps` (file_id, ts → packed scalars incl. fill/evict deltas); `strips` (file_id, ts →
  offset residency, 4-bit quantized + RLE, written only when changed vs previous); `rollups`
  (class, ts → aggregates — the same values that feed the Prometheus gauges, one aggregation
  path); `consumers` (file_id, tgid→role, ts → fill deltas); `annotations` (chain-position
  samples + derived job/episode spans); `streams` (host, neighbors, torrent, devp2p rate
  samples). Consumer attribution comes from the
  fill tracepoint's task context and answers "who reads this file"; note every erigon-family
  process shares `comm="erigon"`, so the drain resolves tgid → role via `/proc/<tgid>/cmdline`
  (cached). Eviction has no consumer attribution on purpose — evictions come from kswapd.
  Fills on inodes *outside* every configured datadir keep their consumer role instead of
  collapsing anonymously: an external process's cache appetite shows as `other × <role>`
  (e.g. `other × lighthouse`), quantifying a coresident CL's IO without tracking its files.
- **Activity annotations (FR6)** — two sources, both zero-touch for the node:
  (a) *metrics poll*: with `--node.metrics.url` (repeatable, paired with `--datadir`), each
  sweep polls the node's own metrics endpoint for chain position (head / execution block) into
  an `annotations` stream (ts → blocks, raw samples); the same poll can sample any other useful
  node gauges (e.g. RPC method rates) as additional correlation streams at zero extra cost. Unwinds make block↔time non-monotonic, so
  block→time lookup returns the matching interval(s) rather than assuming monotonicity.
  (b) *walk-derived job events*: the same lineage machinery that handles FR11 classifies
  background jobs structurally — a new file whose range equals the union of files that
  disappeared is a **merge event** (inputs → output; start ≈ its build/tmp file appearing, end =
  the rename); a new tip-step file with *no* file parents is a **collation event** (its parent
  is MDBX — expect a correlated burst of `mdbx.dat` fills, since collation scans the entity's
  values table). `.tmp`/partial build files never emit events before the rename. Index-build
  events derive the same way later (accessor files appearing) without redesign.
  (c) *prune events are metrics-derived only*: pruning deletes collated steps *inside* MDBX
  (background, post-FCU) — nothing appears or disappears on disk and `mdbx.dat` never shrinks
  (deleted rows feed the freelist), so the walk cannot see it. The poller samples the node's
  prune progress/timing metrics, corroborated by `db_gc_*` freelist deltas; the page-cache
  signature is a dirty/writeback burst on `mdbx.dat` plus fills on the b-tree pages being
  rewritten.
  (d) *unwind + re-exec episodes are derived, not collected*. Unwind and forward exec run as a
  single pipeline — normally the node just execs forward; on a fork switch it unwinds backward
  then execs forward in one go, so there is one episode with two phases, never a standalone
  unwind. Derivation: the execution position stepping backwards opens an episode (depth = prior
  position − unwind target); it closes when forward progress returns to **tip cadence** — the
  catch-up phase advances many blocks per poll, tip-following ~1 — *not* when the old high-water
  mark is regained (the new fork's head may sit below it). To make this trustworthy: the
  annotations poll runs on its own cadence (~15–30 s, one cheap HTTP GET, decoupled from the
  sweep) so episodes register — though a small unwind+exec often completes within one poll and
  shows as a single-sample dip;
  a node-exported unwind counter, where available, is preferred over backstep inference; and
  backsteps adjacent to an endpoint gap open nothing — a restarting node's gauges can
  transiently read low, which must not fabricate a phantom deep unwind. The correlation payoff
  is sharp: blocks re-executed after an unwind were just executed on the other branch, so
  re-exec should be largely cache-served — significant fills/refaults inside a re-exec window
  are avoidable IO by definition, exactly the S3-grade finding FR7 exists for. The rollback
  phase itself shows as `mdbx.dat` history/changeset reads plus state-revert dirty/writeback.
  (e) *host & neighbor pressure context (FR6f)*: each sweep also records host reclaim/pressure
  counters — `MemAvailable`, PSI memory, deltas of `pgscan_kswapd`/`pgscan_direct` and
  `workingset_refault_file` — into a `host` stream (six numbers per sweep, effectively free);
  with repeatable `--watch.cgroup`, sibling cgroups' `memory.current` + `memory.pressure` land
  in a `neighbors` stream. This is the culprit side of the `0.background.md` §5 triangulation,
  stored locally so the scrubber/diff can join it against per-class evictions and job/episode
  spans — the canonical case being an externalcl client (lighthouse/prysm) catching up or
  pruning while our exec refaults.
  (f) *torrent activity (FR6g) is metrics-derived, partially walk-visible*: the downloader both
  downloads (part files appearing/growing — walk-visible) and **seeds** — serving pieces to
  peers reads our `.seg`/`.kv` files through the same page cache, on *peer demand*, uncorrelated
  with any node activity. Upload/download rates polled from the node's metrics form a `torrent`
  stream. Attribution is a ladder: (1) *no privileges* — upload-rate stream × fills on
  cold/frozen classes: correlational, class-level, enough to detect "seeding is causing IO";
  (2) *`--trace.io` + standalone downloader binary* — consumer role `downloader`: per-file,
  byte-exact; (3) *`--trace.io` + embedded downloader (the default)* — the access-mechanism tag
  (§6.3): the node touches snapshots via mmap faults, the seeder via `pread`, so
  **syscall-read fills on seedable files ≈ seeding** even within one process — per-file and
  near-byte-exact. The residual ambiguity on rung 3 is hash-verification/recheck, which also
  reads via syscalls but is whole-file-sequential, burst-shaped, and corroborated by downloader
  state. Seeding served from already-cached pages produces no fills — and no IO, so nothing is
  missed; its pollution side shows as cold-class *residency* rising. The cache consequence is the point: seeding cold historical segments pulls
  them into cache and can evict the hot working set — a prime candidate finding, with real knobs
  (seeding rate limits; an upstream `fadvise(DONTNEED)`-after-serve fix).
  (g) *devp2p serving (FR6h) is the hardest source — correlation-only inside the node*:
  answering peers' eth-protocol requests reads block snapshots through the node's *own* mmap'd
  readers, in the node's *own* process — so neither the consumer role nor the access-mechanism
  tag can isolate it (external sentries don't help: sentry is transport, the data reads stay in
  the node). Attribution rests on three signals: the **class signature** (serving predominantly
  fills frozen blocks classes — headers/bodies/transactions segments — and the receipt domain,
  which tip execution barely touches), the **devp2p egress stream** (outbound bytes/s +
  per-message counters where exposed, polled like the rest), and the **offset-scatter shape**
  (peer requests hit scattered historical ranges; the time×offset heatmap shows it).
  One signature caveat: when receipts/BALs are *not persisted*, serving them **regenerates by
  re-executing the block** — peer demand then reads state/history/II classes, mimicking
  execution. The range/tier dimension still separates the case that matters: old-block
  regeneration fills *frozen* history/II ranges tip exec rarely touches, while recent-block
  regeneration is mostly cache-served (little physical IO to attribute). Regen re-execs are
  read-only replays — the chain-position stream does not move, so they can never fake an unwind
  episode. These findings carry their own knobs: persistence flags vs regeneration IO, and
  generator cache sizes. The main
  confounder, historical RPC, is separable when rpcdaemon runs standalone — fault fills
  attribute to the *faulting* process, so it gets its own consumer role; the residual
  within-node split (exec vs serve vs embedded RPC) is code-path attribution, i.e. the Phase 4
  `kvmetrics`/blockReader `source` extension if ever needed. When reading rpcdaemon's
  role-split fills, expect them on history/II classes *and* on latest `.kv`: temporal reads
  fall through to latest state for keys unchanged since the queried block
  (`DomainRoTx.GetAsOf` → `GetLatest`), so `.kv` is a working set shared with tip exec by
  construction, while `.v`/`.ef`/`.efi` are near-exclusively historical territory. Discovery-DB and txpool traffic
  need nothing special — they land in their own mdbx classes (`nodes/<proto>`, `txpool`).
  Every time-axis view can label time T with block N and overlay merge/collation/prune/unwind
  spans; without the metrics flag, block labels, prune spans, unwind episodes, and the
  torrent/devp2p streams are absent — merge/collation events and the host stream still work (they need only the
  walk and `/proc`), and prune's dirty/writeback signature remains visible, just unlabeled.
- **Explainability (FR7)**: fill deltas land in the same sweep rows as `recently_evicted`,
  letting the UI classify IO per class/file as **warmup** (first touch of a region), **refault**
  (recently evicted and re-read — the avoidable kind), **steady-state**, or **background-job**
  (inside a merge/collation/prune span: merge reads on the sources — sequential, through the one
  view where readahead is deliberately on — merge/collation writes on the destination, collation
  scan fills on `mdbx.dat`, prune's dirty/writeback + b-tree rewrite fills on `mdbx.dat`,
  **seeding** — syscall-read-mechanism fills on seedable classes per the §6.4(f) attribution
  ladder, corroborated by the torrent upload-rate stream — and **peer serving** — fills on
  block/receipt classes correlated with the devp2p egress stream, §6.4(g)).
  Unwind/re-exec episodes add no category of their own — fills inside them keep their kind but
  carry the episode tag, because "refault during re-exec" is precisely the avoidable-IO signal;
  with `KV_READ_METRICS` enabled on the node, logical read rates from `kvmetrics` overlay
  physical fills to separate "code asked too much" from "cache couldn't hold it" (§7).
  Merge awareness is load-bearing here (FR11): deleting a merged-away file *invalidates* its
  pages, which fires the same eviction tracepoint as reclaim — so evictions on a file that
  disappears in the same or adjacent sweep classify as **deleted** and are excluded from thrash;
  fills on a freshly-minted merged file within its lineage window classify as **merge warmup**,
  not working-set pressure. With the store enabled, the exported fill counter also gains this
  classification as a class-level `kind` label
  (`pagecache_fill_bytes_total{...,kind="warmup|refault|steady|background|deleted"}`,
  cardinality ×5, still hundreds of series) — so "sustained refault fills on a class" is a
  Grafana alert rule, while the file/region/consumer/episode drill-down stays in the UI.
- **Volume**: 10k files at 5-min cadence ≈ 3M scalar rows/day → tens of MB/day compressed.
  Strips dominate: adaptive bucket counts (16–1024 by file size, ~128 avg) ≈ 370 MB/day raw,
  but residency is spatially coherent (long RLE runs) and temporally stable (unchanged strips
  are skipped) → expect 10–40 MB/day in practice. Retention: full fidelity 7–14 days, then
  downsample or drop; hard cap `--store.max-size`, oldest-first pruning. `--store.dir` defaults
  outside any monitored datadir; if placed inside one, the walker excludes it and labels the
  store's own footprint `sub="mmapviz"`.
- **Non-goals**: no query language, no HA/backup, no cross-host aggregation — only the known UI
  query shapes (time range × file/class × metric; strip history; top movers; two-point diff).

### 6.5 Explicit non-choice — no new instrumentation inside domain read/write paths

Considered and rejected for the stated goals. The *logical* side of this idea already exists as
`db/state/kvmetrics` (`kv_read_count{source,domain,op}`, off by default behind
`KV_READ_METRICS`): it answers "which code path issued how many reads against files vs DB vs
cache". What it structurally cannot answer — and what no userspace counter can — is whether those
reads hit the page cache or the disk, and which bytes the kernel pulled or evicted. That physical
half is exactly Components A–C. Reasoning in §7.

## 7. Decision: background sampling vs instrumenting reads/writes

| Aspect | In-node background sampler (considered, not chosen) | Sidecar: sampler + CLI + eBPF tier + history store (chosen) | Inline in domain read/write path (exists today as `kvmetrics`) |
|---|---|---|---|
| Sees page-cache truth (readahead, evictions, other processes, MDBX internals) | yes (cachestat) | yes (cachestat/eBPF see everything) | **no** — userspace can't tell hit from miss without a syscall per access |
| Hot-path cost | zero (own goroutine, no locks shared with queries) | zero for the node | atomic per access; our parallel-exec history shows one hot atomic can cost 3–5× in contended loops |
| Physical IO attribution | indirect (evicted/recently_evicted deltas) | exact (tracepoints, bytes incl. readahead) | wrong tool — a "read" that hits cache does no IO; a miss also pulls readahead it never sees |
| Coverage | all mapped files incl. mdbx.dat and torrent | same, plus other processes | only instrumented call sites; misses MDBX (C library), misses readahead/evictions entirely |
| Privileges / deployment | none; gauges appear on the node's existing endpoint | none for sampler/CLI tiers, `CAP_BPF`+`CAP_PERFMON` for `--trace.io`; one extra unit + scrape target | none |
| What it uniquely offers | no extra unit to run; visible through the `erigon support` tunnel | zero node changes; exact IO; one instance covers all nodes on a host; independent restart/upgrade; external CPU cap; works even while the node is down or crashed | **logical** per-call-site attribution: "which API/stage asked for these bytes" |

Recommendation: **everything in the sidecar** — unprivileged tiers (A+B) everywhere, `--trace.io`
(C) where wanted. The in-node variant's one real advantage is deployment convenience: gauges on
the node's existing metrics endpoint, no extra unit, visibility through the `erigon support`
tunnel. We trade that for zero node-code risk, an independent release/restart cadence, one
collector per multi-node host, and a hard external CPU cap. The collection code is
process-agnostic, so re-hosting the sampler in-node behind a flag remains a cheap fallback if
running an extra unit ever proves a burden in practice.

**Why not OTEL tracing for code-path attribution** (evaluated on request, not adopted): spans
name code paths, but attributing a *kernel* fill to a span requires bridging kernel task context
to the active goroutine — Go's M:N scheduling means `tid` ≠ code path, so the bridge needs
eBPF reading the `g` pointer at Go-version-specific offsets plus node-side goid→span
bookkeeping on every span boundary: fragile, Go-release-coupled, and hot-path-expensive (a span
per domain read is far heavier than the one hot atomic that cost 3–5× in parallel exec; sampled
spans attribute only coincidentally-sampled fills). Once such a bridge exists, a one-byte
per-goroutine activity tag delivers the same attribution without the SDK — OTEL adds
cross-service propagation, which page-fault attribution inside one process never uses. The
robust route is the layer split below; if erigon ever adopts tracing for its own reasons,
mmapviz joins those span windows against the store at class level for free.

Inline instrumentation is the only way to answer
"which *code path* caused the traffic" — and that half already exists (`kvmetrics`, per
source×domain, off by default; our parallel-exec history shows why hot-path atomics stay opt-in).
Turning `KV_READ_METRICS` on alongside the new physical metrics gives the full picture: logical
reads per code path (kvmetrics) joined with physical fills/evictions per file class (this design)
on one dashboard. The exec-vs-RPC split in particular is solved on a ladder: *standalone
rpcdaemon* → physical fills split by consumer role, per file, exact (a deployment choice, not
code); *embedded* → kvmetrics already carries both `source=exec` and `source=rpc` per domain, so
the logical demand split exists today and joins against per-class fills — and RPC's
`op=file`-reads-to-fills ratio is its cache-hit rate. Cache *contents* never split in either
mode: a resident page serves both consumers; only flows attribute. Extending kvmetrics to per-*file* labels is filed as optional Phase 3, only if a
concrete investigation ever needs per-code-path × per-file resolution — never per-byte, never as
the source of footprint/IO metrics.

## 9. Performance budget

| Item | Measured / derived | Budget stance |
|---|---|---|
| cachestat, cold file | 2.4 µs per 4 GiB (≈ free) | cost scales with resident, not datadir size |
| cachestat, warm file | 123–148 ns per resident 4 KiB page (order-0 worst case; large folios cost proportionally less) | 100 GiB resident ≈ 3.5 s CPU/full pass |
| Sampler at default cadence | full pass ≤ 5 min, self-tuned | target ≤ 0.5% of one core, self-enforced + externally cappable (cgroup) |
| mincore heatmap, on demand | ~45–145 ns/page → 32 GiB file ≈ 0.4–1.2 s | on-request only, rate-limited |
| eBPF tracepoints | ~100 ns/event in-kernel; 2 GiB/s of fills ≈ 512k events/s ≈ ≤5% of one core *during* such bursts, zero idle | sidecar-only, opt-in |
| smaps/pmap | seconds per scan on TB mappings + target mmap_lock (read) | excluded from periodic paths |
| History store writes | ~10–40 MB/day compressed (§6.4) | bounded by `--store.max-size`, oldest-first prune |
| Node fault/query paths, node binary | untouched | guaranteed — the node runs zero new code |

## 10. Risks & caveats

- **Kernel < 6.5**: no cachestat → the sidecar maps each file read-only and falls back to chunked
  `mincore` (truthful as datadir owner), or the feature turns off. Fleet is on 6.8.
- **mincore truthfulness** (post-5.2 kernels): reports page-cache state only when the caller could
  write the file; run tooling as the datadir owner (we do).
- **Large folios**: fill/evict byte accounting uses the tracepoint `order` field (present on 6.8);
  cachestat counts pages exactly; mincore bitmaps are per-4KiB regardless of folio size.
- **Cardinality**: per-file Prometheus series are deliberately not exported; the class label set is
  bounded (~hundreds). Adding a per-file opt-in flag later must keep a hard series cap.
- **Inode churn**: snapshot merges continuously delete smaller files and mint bigger ones. The
  sampler re-walks the datadir each pass (no stale fds held); the tracer re-resolves on unknown
  inodes and tolerates deleted-but-open files; history keeps tombstoned rows and lineage so past
  layouts and merge-induced IO stay interpretable (§6.4).
- **Double mapping / mixed access**: the same inode can be mapped twice by the node (main
  `MADV_RANDOM` map + transient sequential view), read via plain file IO by the torrent seeder,
  and written during builds — page cache is per-inode, so `(dev,ino)` dedupe keeps footprint
  honest, and kernel-side fill/evict attribution is correct regardless of which fd or mapping
  triggered it.
- **Shared hosts**: several nodes share one page cache. Per-file attribution stays correct per
  datadir; host-level `Cached` panels are context, not per-node truth. `nr_evicted` /
  `nr_recently_evicted` are shadow-entry based and can age out — treat as signal, not accounting.
- **tmpfs datadirs** (dev runs): cachestat/mincore still work (tmpfs is page cache); "resident"
  then means "exists", and eviction signals are meaningless there.
- **Sidecar/datadir version skew**: class labels come from the name parsers compiled into the
  binary; shipping mmapviz as a command of the main `erigon` binary keeps parsers and datadir
  layout in lockstep. An older sidecar against a newer layout degrades to `ext`-only labels,
  never wrong byte counts.
- **Run it as the datadir owner**: `cachestat` needs only a readable fd, but `mincore` heatmaps
  are truthful only for an owner/write-capable caller (§3); same-user is the simple safe policy.
- **Containers**: the sidecar needs the datadirs mounted (residency is per-inode, so a different
  mount path is fine); `--trace.io` additionally needs host-level privileges, and its tracepoints
  see the whole host — filtering to configured datadirs happens at inode-resolution time.
- **`erigon support` tunnel**: sidecar metrics live on their own listener and are not visible
  through the node's diagnostics tunnel; Prometheus/Grafana is the intended consumer.
- **Store degradation**: disk-full or store IO errors degrade the sidecar to metrics-only
  (sampling and Prometheus export continue, history pauses, self-telemetry says so) rather than
  crash-looping. Wall-clock jumps are absorbed by monotonic sweep sequencing (ts stored, seq
  ordered).
- **Store self-observation**: the store is itself an mdbx file in page cache; it is excluded
  from (or labeled apart in) its own measurements — see §6.4.
- **Endpoint exposure**: `/debug/pagecache`, the `/api/v1/*` history endpoints, and `/ui` reveal
  access patterns and datadir layout; the listener ships no auth and binds loopback by default.
  Remote viewing goes over an SSH tunnel (`ssh -L 6070:localhost:6070`) or VPN; if internet
  exposure is truly wanted, front it with a TLS + auth reverse proxy — never bind it raw to
  `0.0.0.0` (`2.visualisations.md` §5).
